# 1. 核心设定

## 1.1 器灵形态

**[CONFIRMED]**

每把喵刀都具有“器灵形态”。

- 平时，剑以**猫娘器灵**的实体形态跟随持有者。
- 进入战斗时，器灵会重新化为剑。
- 普通喵刀与暗黑喵刀都属于这一系统。
- 普通器灵的主题色为**粉白**。
- 暗黑器灵的主题色为**粉紫**。

器灵不是独立于剑的第二件物品。她与剑应当被视为**同一件武器、同一个身份、两种形态**。

```text
同一个 Blade Soul
        │
        ├─ Spirit Form：猫娘器灵实体
        │
        └─ Sword Form：ItemStack 剑
```

工程约束：同一个身份可以有档案、客户端缓存及暂存副本，但只能有一个可参与玩法的有效载体。
托管在服务端档案中的原剑序列化数据不是第二把可交易、可攻击的剑。
以下类名、数据层和算法均为 **[PROPOSED] 技术提案**，不因写入本文而成为已经实现的功能。

# 2. 形态状态机

## 2.1 推荐状态 [PROPOSED]

```text
SWORD -> MATERIALIZING -> SPIRIT -> RECALLING -> SWORD
                  \         |         /
                   -> RECOVERY_PENDING
```

- `SWORD`：一个经过校验的实际剑物品是有效载体。
- `MATERIALIZING`：显现交接中。源物品、暂存数据及新实体的有效性由交接服务管理。
- `SPIRIT`：一个匹配 soulId、实体 UUID 和状态修订的猫娘实体是有效载体。
- `RECALLING`：召回交接中，停止跟随、交互和重复召回。
- `RECOVERY_PENDING`：工程恢复状态，不是已经确认的休眠、复活或破损玩法。

战斗状态与形态分开保存或推导。不要额外保留一套与 `SWORD` 冲突的
`SWORD_IN_COMBAT` 形态字段。是否进入战斗只决定转换请求何时发出。
原草案的 `TRANSFORMING_TO_SPIRIT` 对应 `MATERIALIZING`，
`TRANSFORMING_TO_SWORD` 对应 `RECALLING`，不要重复实现两套状态机。

## 2.2 单一交接入口 [PROPOSED]

所有显现、召回、死亡回剑均经 `SpiritTransformationService`，
不得在物品右键、实体死亡和网络处理器里各自生成剑。
服务端串行处理写操作，验证 `soulId`、主人、当前状态、`revision` 和 `operationId`。
同一 operationId 重发应返回已有结果或拒绝，不得再次执行。
客户端只能发送意图，不能提交好感数值、原剑数据或任意主人 UUID 作为事实。

## 2.3 剑变器灵 [PROPOSED]

1. 校验实际持有者、绑定规则、源槽位、源 ItemStack 和当前形态。
2. 保存完整原剑快照、来源定位、事务编号和预期 revision，进入 MATERIALIZING。
3. 预检实体出生位置及实体添加条件。新建实体在交接提交前不得参与玩法。
4. 移除经过再次核验的那一个原剑实例，确认新实体确实被世界接受。
5. 更新档案的有效载体和修订，激活实体并广播显示状态。
6. 失败时根据操作记录回滚或进入恢复流程，不能无条件再发一把剑。

这是交接协议要求，不是具有磁盘事务保证的现成 API。
具体调用顺序须在所用加载器实际事件与实体添加 API 下验证，
且任何外部可观察点都不得让两个载体同时有效。

## 2.4 器灵变剑 [PROPOSED]

1. 校验 soulId、主人的权限、实体 UUID、形态及 revision。
2. 冻结本实体的交互与 AI，创建唯一 RECALLING 操作记录。
3. 从托管快照恢复原剑，应用本次合法变化，而非只用阶段 ID 创建空白新剑。
4. 由 `SwordDeliveryPolicy` 预检目标位置并交付，保留可恢复记录。
5. 提交单一有效载体后，移除猫娘并同步客户端；不得由动画结束回调发放物品。

严禁直接覆盖玩家主手或副手已有物品。正式落点、是否强制换手、满背包回退均为 TBD。
调试阶段可以要求指定空槽位，否则明确失败，不擅自选择正式掉落规则。

## 2.5 崩溃恢复与限制 [PROPOSED]

UUID 仅识别身份，不能独自防复制；单 tick 完成也不等于多个存档文件原子落盘。
需要记录 pendingTransition、有效载体和版本，并在实体/玩家加载时核对。
恢复目标是重复执行不重复扣罚、不重复交付、不静默丢失原剑。
证据不足时冻结冲突状态并记录诊断，不猜测哪份数据更新，不直接销毁培养数据。
正式发布前必须注入交接中断，验证服务器重启后的恢复。

# 3. Blade Soul 身份与存储

## 3.1 三层架构 [PROPOSED]

器灵档案是长期身份，剑与猫娘分别是两种表现和玩法载体。

| 层 | 推荐对象 | 权威职责 |
| --- | --- | --- |
| 长期档案 | `BladeSoulRecord` / `BladeSoulStore` | 身份、关系好感、主人、路线、阶段、载体状态与交接记录 |
| 剑物品 | 实际 `ItemStack` + 自定义引用组件 | 剑形态时的耐久、附魔、自定义名等实际物品数据 |
| 猫娘实体 | `BladeSpiritEntity` | 实体形态的移动、生命、交互；引用同一个 soulId |
| 客户端显示 | 必要同步字段 | 只读显示，不反写权威好感或交接状态 |

普通和暗黑目前只需一个器灵实体类型，通过路线和阶段选择外观。
不强制依赖车万女仆，不为 17 个阶段复制 17 套实体逻辑。

## 3.2 推荐数据字段 [PROPOSED]

```text
BladeSoulRecord
  soulId: UUID
  ownerId: Optional<UUID>
  route: BladeRoute
  stage: int
  affection: numeric value with validated bounds
  form: SpiritForm
  revision: long
  activeEntityId: Optional<UUID>
  storedSword: Optional<serialized ItemStack>
  spiritHealthSnapshot: Optional<health state>
  pendingTransition: Optional<TransitionRecord>
  schemaVersion: int
```

```text
TransitionRecord
  operationId
  expectedRevision
  sourceForm / targetForm
  sourceLocator / intendedDestination
  sourceSnapshot
  deathPenaltyOrOtherDelta
  phase
```

`soulId` 与旧文档中的 `bladeSoulId` 是同一概念；`ownerId` 与 `ownerUuid` 同理。
旧的 `BladeSoulData` 是概念草案名，不应在新档案之外再做第二个可独立修改的数据源。
如果实现前仓库已有命名或持久化格式，应迁移/兼容，不能只为对齐本文而破坏存档。
数值存储类型和字段名是提案，不代表最终好感范围已确认。

## 3.3 初始化与缺失数据 [PROPOSED]

仅服务端可以为真正未初始化的实际 ItemStack 建立新身份。
不能在物品注册时生成所有剑共用的 UUID；不能在 tooltip、getter、渲染、每次登录或变身时重建身份。
默认物品注册配置中不要放每实例 UUID。物品拷贝会拷贝数据，不能假设 UUID 自然防重。
两把新初始化的同阶剑应有不同身份；同一把剑变形和升阶保留身份。

已经携带 soulId 却查不到档案时，不自动当新剑，不自动重置好感或给复制品分配新 ID。
先区分缺失档案、旧格式、外部存档导入和真正新物品，再走明确迁移/恢复入口。
跨服务器导入、交易、创造复制及管理员修复规则还需设计；不宣称本地身份可自动跨存档通用。

## 3.4 持久化落点 [PROPOSED]

推荐 `BladeSoulStore` 统一访问 Minecraft 服务器级 SavedData。
26.1 起服务器具有全局数据存储入口；26.2 应检查实际依赖源码并优先使用服务器实例，
不要照搬旧教程把全局器灵档案分别存在每个维度或固定存在主世界。
修改档案后须按 SavedData 机制标记需要保存，但 `setDirty` 不等于已经完成磁盘事务。[T1][T2]

ItemStack 使用自定义数据组件保存 soulId 等必要引用。组件值应遵守该版本的数据组件约定，
更新时重新设置结构化值，而不是把多个物品共享的可变对象当成独立数据。[T3]
客户端缓存只是同步快照；实体和剑不得各保存一份可独立增长的好感。

## 3.5 原剑数据交接与升阶 [PROPOSED]

剑形态下：真实 ItemStack 的物品属性有效，档案里若有恢复备份则明确是非权威备份。
器灵形态下：完整原剑数据托管到档案，不能再在玩家背包保留同一把可攻击的剑。
同阶召回应恢复原有耐久、附魔、名字及支持的自定义组件，不重新创建只有种类的空剑。

升阶不同于同阶变形：以目标阶段的新物品默认属性为基础，通过显式迁移策略保留身份和关系数据。
不要盲目复制全部旧组件，导致新阶攻击属性、耐久上限又变回旧值。
附魔、剩余耐久比例、名字及第三方组件的最终升阶策略仍为 TBD。
记录和物品路线/阶段冲突时报告并阻断交接，不静默任选一份覆盖另一份。

# 5. 平时跟随

## 5.1 固定行为

**[CONFIRMED]**

非战斗状态下，喵刀可以猫娘器灵形态跟随玩家。

## 5.2 推荐 AI [PROPOSED]

建议建立基于 `PathfinderMob` 的自定义 `BladeSpiritEntity`，先用占位模型。
Fabric 26.2 官方实体教程提供该基类、注册、属性、目标与模型的示例，
具体方法签名应以两加载器当前映射依赖为准。[T4]

推荐优先级：转换中暂停其他行为 -> 基础避险 -> 跟随 -> 看向主人与闲置。
可用自定义 `FollowBladeOwnerGoal` 协调已有导航；不要假设名为 FollowOwnerGoal 的类
无需满足其原有驯养实体约束就能直接套用。其他目标名称只是职责，不是保证存在的 API。

跟随开始/停止距离分离以减少抖动；限制重算路径频率；传送补位前验证空间、地面、危险方块及已加载区块。
主人离线不累计陪伴，不为寻找主人强制加载大量区块。
不擅自加入主动战斗、繁殖、交易、恋爱或开门破坏行为。
第一版安全跟随的参数可以作为明确标注的可修改测试配置，不伪装为用户正式决定。

**[CONFIRMED]**

# 7. 好感度

## 7.1 核心

**[CONFIRMED]**

好感度是喵刀升级的**必要条件**。

提升来源至少包含：

1. 与器灵相处。
2. 与器灵互动。
3. 与器灵共同战斗。

器灵死亡会降低好感度。

## 7.2 好感度的含义

**[CONFIRMED mechanics / DRAFT lore]**

好感度代表玩家与器灵之间的关系强度、信任与默契。

它不应默认等于恋爱值。

除非用户以后明确设定恋爱系统，否则：

- 不写“老婆值”。
- 不默认恋爱台词。
- 不把高好感必然解释为恋爱关系。

## 7.3 数据归属

**[PROPOSED, strongly recommended]**

好感度属于器灵身份及其当前关系档案，不是属于某个阶段 item ID；通过 `AffectionService` 修改 `BladeSoulRecord`。


# 8. 好感度来源

## 8.1 相处

**[CONFIRMED]**

**[PROPOSED anti-AFK design]**


- AFK 刷满。
- 数据频繁写入。
- 多实体服务器性能差。


- 器灵确实处于 Spirit Form。
- 主人在附近。
- 双方在同维度。
- 不是刚加载的假在线状态。

# 10. 器灵生命与死亡

## 10.1 器灵可以死亡

**[CONFIRMED]**

器灵实体死亡后：

1. 不永久消失。
2. 变回剑形态。
3. 好感度下降。
4. 剑耐久下降。

这应当让死亡成为明显损失，但不是直接删除整个长期培养对象。

## 10.2 死亡转换顺序 [PROPOSED]

`SpiritDeathHandler` 只产生带死亡原因的转换请求，仍走统一交接服务，不另做剑掉落通道。

1. 服务端确认有效死亡及当前实体身份，区分真正死亡和普通移除/卸载。
2. 以显现身份、修订及死亡操作编号去重，冻结本次实体。
3. 从档案和原剑快照读取数据，按已确认配置计算好感与耐久损失。
4. 将本次损失结果与交接阶段记入同一恢复记录。重复死亡回调不得再次扣罚。
5. 从原剑恢复，应用一次损失，由 SwordDeliveryPolicy 交付。
6. 交接提交后清理旧实体；失败进入 RECOVERY_PENDING，保留数据及未交付状态。

默认战利品和自定义死亡掉落不得再发第二把剑。
生命归零、死亡动画结束、实体移除等多个回调不能分别发奖或扣罚。
未确定的扣值和正式交付位置由规则提供；只可使用明确的测试注入，不把测试值当最终玩法。
